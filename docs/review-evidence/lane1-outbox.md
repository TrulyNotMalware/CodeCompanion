# 3차 리뷰 — outbox · relay · CDC · Kafka 레인 보고

**검증 방법**: 소스를 직접 읽었고, 라이브러리 동작은 jar 바이트코드(`javap`)로 확인했습니다. 메인 세션의 전체 빌드와 충돌하지 않도록 테스트는 돌리지 않았습니다. 따라서 이 보고는 정적 분석과 바이트코드 확인 결과입니다.

**결론**: 13.5가 반영했다고 한 A2·A3·S9·S17의 핵심 정합성은 코드에서 해결됐습니다. 소유권 토큰, 발송 예산, `:now` 바인딩, PENDING만 claim, 상태 기록 실패를 리스너 밖으로 내보내지 않는 것, DLT 배선이 모두 들어가 있습니다. 토큰 ABA, 오버플로, NULL 행, 경로 간 이중 발송은 찾지 못했습니다.

새로 찾은 결함 중 가장 중요한 것은 O1입니다. 복구 스윕이 relay 큐를 넘친 작업을 CallerRuns로 스케줄러 스레드에서 직접 실행하는데, 가상 스레드 모드에서는 모든 fixed-delay 작업이 그 스레드 하나를 공유합니다. 그래서 리마인더·스탠드업·아젠다·보존·CVE 작업이 수십 분 멈출 수 있습니다.

## 3. 확인했고 문제 없던 것

- **토큰 전이 전부가 조건부**: `claimPending`/`reclaimStuck`만 `attempt_count`를 올리고, 둘 다 읽은 값을 조건으로 겁니다. `renewClaim`/`deferClaim`/`completeClaim`/`abandonStuck`은 모두 `attempt = :attemptCount AND status = 'IN_PROGRESS'`이고, reclaim/abandon에는 나이 조건도 있습니다.
- **ABA·재사용·오버플로·NULL**: `attempt_count`는 증가만 합니다. PENDING으로 되돌리는 문장이 없어 토큰이 재사용되지 않습니다. 24시간 상한이라 INT 오버플로는 불가능합니다. V20/V22와 Hibernate `update` 모두 `NOT NULL DEFAULT 0`이라 NULL 행이 없습니다. V20 이전 after-image는 DB를 다시 읽으므로 영향이 없습니다.
- **경로 간 인터리빙**: CDC·스윕 stale claim은 attempt CAS로 한쪽만 이깁니다. 스윕끼리(파드 2개) reclaim과 abandon도 CAS입니다. 큐에서 대기하던 작업과 스윕 reclaim이 겹치면 renew나 reclaim 중 하나만 통과합니다. 리밸런스로 재전달되면 IN_PROGRESS를 건너뜁니다. CDC와 폴링은 조건상 배타적입니다.
- **defer 산식**: `updated_at = min(now+wait, created+24h) - 300초`로, 스윕 적격 시점이 정확히 `now + wait`입니다. `GREATEST(send_count-1, 0)`이라 음수가 되지 않습니다. 헬스의 60초 유예와도 맞습니다.
- **트랜잭션 경계**: relay에 `@Transactional` self-invocation이 없습니다. 리포지토리 호출은 각자 자기 트랜잭션입니다. 결과 이벤트의 유일한 소비자인 `StandupSummaryService.replaceSummaryMarkerWithSlackTs`는 동기 `@EventListener`이고 예외는 catch됩니다. `saveOutboxMessage`(BEFORE_COMMIT)의 3회 재시도는 사실상 무의미합니다(merge의 INSERT가 커밋 시점 flush에서 나감). 하지만 결과는 롤백이라 정합성 문제는 없습니다(main 기존).
- **보존 purge**: `status IN ('SUCCESS','FAILURE')`만 지우므로 PENDING·IN_PROGRESS는 지울 수 없습니다. CDC가 아직 소비하지 않은 레코드의 행이 먼저 지워져도 리스너가 "row missing" 경고 후 건너뜁니다. delete 이벤트와 tombstone은 무시합니다.
- **DLT 세부**: 역직렬화 실패 레코드는 원본 바이트가 bytes 템플릿으로 갑니다(`findTemplateForValue` 순서). `DeserializationException`은 `DefaultErrorHandler` 기본 비재시도 대상입니다. `CdcRecordParseException`도 비재시도로 등록돼 있습니다.
- **테스트 기대값**: 13.4가 지적한 결함 고정 테스트(`:112-125`)는 반전됐습니다. H2 시나리오 테스트(`OutboxRelayRecoveryScenarioTest`)의 기대값 17/3/1도 설계와 맞습니다. 다만 모든 테스트가 inline executor나 `QueuedExecutor`를 써서 O1·O2(큐 포화, 스케줄러 스레드)는 구조적으로 잡을 수 없습니다.
- **Debezium 스냅샷 시각 변환**: `toOutboxMessage`는 `systemDefault` 존을 쓰고 micro 단위를 가정하지만, 스냅샷의 시각 필드를 더 이상 쓰지 않아 영향이 없습니다.

## 4. 미검증으로 남긴 것

- 테스트를 실행하지 않았습니다(메인 빌드와 락 경합을 피하려고). 모든 판정은 정적 분석과 바이트코드 확인입니다.
- prod 값: `SQL_PROD_CONNECTION_TIMEOUT`, prod `outbox_message`의 `created_at`/`updated_at` 컬럼 타입(DATETIME/TIMESTAMP)과 세션 존. 쓰기와 읽기가 같은 세션 존이면 대칭이라 무해하다고 봤습니다.
- 렌더의 `JdkClientHttpRequestFactory`에서 connect 3초 + read 10초가 DNS와 본문 읽기까지 상한을 거는지(Spring 7 동작). 이것은 dispatch 레인 범위입니다.
- 실제 브로커 상에서: `KafkaAdmin`이 ACL 거부 시 기동을 계속하는지, DLT 왕복, `commitSync` 실패 시 컨테이너 동작.
- **범위 밖이지만 같은 S2 계열이 남아 있음 (다른 레인 확인 요망)**:
  - CVE: `CveSummaryWorker.kt:25`가 `LocalDateTime.now()`(JVM, 서울)로 컷오프를 만드는데, `JpaCveEventRepository.kt:82,118,134`는 `updated_at = CURRENT_TIMESTAMP`(DB, UTC)로 씁니다. UTC DB라면 방금 claim한 요약이 즉시 stuck으로 리셋될 수 있습니다(main 기존).
  - 스탠드업: `JpaSessionDispatchRepository.kt:36,51,68,84`는 `CURRENT_TIMESTAMP`로 쓰고 `Instant` 컷오프와 비교합니다. Hibernate가 Instant를 TIMESTAMP_UTC로 바인딩하면 UTC DB에서는 일치할 가능성이 있으나 미검증입니다.
