### 2. 확인했고 문제 없던 것
- **MCP 요청별 신원 분리**: `WebMvcStreamableServerTransportProvider`(mcp-spring-webmvc 2.0.1)의 `handlePost`/`handleGet`/`handleDelete`는 요청마다 `contextExtractor.extract`를 호출하고 결과를 `contextWrite`로 넘깁니다. `McpStreamableServerSession`(mcp-core 2.0.0)은 요청마다 reactor 컨텍스트로 새 `McpAsyncServerExchange`를 만듭니다(javap 확인). 따라서 같은 MCP 세션 ID를 공유해도 다른 사용자의 신원이 섞이지 않습니다.
- **필터와 contextExtractor**: 둘 다 첫 번째 `Authorization` 헤더와 `"Bearer "` 접두사를 같은 방식으로 처리하고, 같은 `verify`를 호출합니다. 필터는 `FilterRegistrationBean.urlPatterns`로 컨테이너가 디코딩한 경로에 매칭되므로 라우터 매칭과 일치합니다.
- **토큰 코덱과 로깅**: 비교는 `MessageDigest.isEqual`(상수 시간)이고 버전 고정, 만료+skew를 검사합니다. 토큰을 로그나 거부 응답 본문에 쓰는 곳은 없습니다. TTL 300초가 사이드카 타임아웃 120초보다 깁니다.
- **도구 범위**: 모든 도구가 user id 인자를 받지 않습니다. `list_meetings`는 주최자이거나 참가자인 회의만 조회합니다(`JpaMeetingRepository.kt:40-52`, 취소 회의 제외). `get_status`/`list_roles`는 호출마다 역할을 다시 해석합니다.
- **ephemeral 버튼 라우팅**: 회의 목록(ephemeral)의 Reschedule/Add participant/Cancel 버튼은 모두 `isPrimary=true`(`ActionElementTypes.kt:7-9`)라 버튼 `value`로 라우팅이 정상 동작합니다.
- **`private_metadata`**: 서버가 설정하고 Slack이 보관하므로 사용자가 바꿀 수 없습니다. 호스트 권한은 리포지토리에서 강제합니다. 모달 제목(24자)과 metadata(3000자) 한도 안이고, 스탠드업 모달은 최대 9블록, label ≤200자입니다.
- **회의 목록 블록 수**: 16건일 때 헤더 2 + 47 + 생략 안내 1 = 정확히 50블록입니다. 회의별 `action_id`/`block_id`도 고유합니다.
- **decline 검증 응답**: `response_action: errors` JSON 형식이 맞고 input `block_id`를 키로 씁니다.
- **빈 옵션 방지**: CVE 토픽 목록이 비면 모달을 열기 전에 안내합니다. 헤더 없는 Text는 Ephemeral/Replace에만 쓰여 빈 header 블록이 생기지 않습니다. `/meetup list`의 이중 공백 토큰은 걸러집니다.
- **Socket Mode**(local 전용): interactive는 처리 후 `response_action`을 ack에 실어 보내고, slash/event는 먼저 ack합니다. `start()`는 예외를 던지지 않습니다.
- **에이전트 응답 경로**: 컨텍스트 이름 정화(S19 반영), Busy는 ephemeral, 회신 스테이징 실패는 `checkNotNull`로 롤백합니다.

### 3. 미검증으로 남긴 것
- **자기 멘션 루프**: 봇이 자기 멘션(`<@BOT>`)이 담긴 메시지를 게시했을 때 Slack이 app_mention을 발송하는지 확인하지 못했습니다. `SlackMentionMapper`는 `event.bot_id`/`user == bot`을 거르지 않고, `EventCallbackData.botId`는 파싱만 하고 쓰지 않습니다. 발송된다면 AI 답변을 매개로 루프가 생길 수 있습니다.
- **A4의 성립 조건**: 사이드카가 다른 `X-User-Id`로도 같은 provider 세션을 재개하는지는 외부 저장소라 확인하지 못했습니다.
- **A6의 알림 발화**: 봇이 게시한 section 블록이나 스레드 답글 안의 `<!channel>`이 실제로 알림을 발화하는지 확인하지 못했습니다(공개 문서 지식으로는 발화). rich_text의 `text` 요소가 `<`를 이스케이프하지 않은 원문으로 오는지도 마찬가지입니다(notice 경로).
- **A7**: 운영 MariaDB의 `sql_mode`가 strict인지(오류가 나는지, 조용히 잘리는지) 확인하지 못했습니다.
- **A8**: Jetty 12 `ForwardedRequestCustomizer`가 XFF로 원격 주소를 덮는 세부는 Jetty 문서 기준이고 바이트코드로는 보지 않았습니다. Boot가 k8s에서 이 customizer를 추가한다는 점만 javap로 확인했습니다. `/mcp`가 외부 ingress에 노출되는지도 저장소 밖 정보입니다.
